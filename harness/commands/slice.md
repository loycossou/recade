## Step 1. The project, the sheet and the dependencies

1. Check the first word of the arguments. It must match `S-` followed by two digits and an optional lower-case letter. If it does not, say "Usage: /slice S-nn. Run /status to see the slices." and stop. Never put a value that did not match into a command. Call it `<S-nn>` from now on.
2. Run `recade state show --json`. <!-- shared:no-project -->If it exits 1 with "No Recade project here", say so in one line, suggest `/recade:new <project>`, and stop.<!-- /shared:no-project --> <!-- shared:unlinked-repo -->If it exits 1 with a message that names `recade repo sync`, this repository is not linked to its workspace (the link is missing, or names another workspace): show the message, say that nothing was written, and stop. Do not run `recade repo sync` yourself: the owner runs it from the workspace.<!-- /shared:unlinked-repo --> If it exits 2, show the error and stop. Read `languages`, `second_opinion`, `gates`, and `github` (its `owner` and `repo` are the workspace repository, which holds the issues). The required gates are not read here: each code repository has its own, in its `.claude/recade.yaml` (see the gates rule of Step 2). If gate `G4` is not passed, say the slices are not approved yet, suggest `/recade:slices`, and stop.
3. From here on, answer in the language of `languages.chat`. Keep Recade keywords in English: slice, gate, lane, harness, BIBLE, PLAN, DEC, retro. <!-- shared:id-gist -->When you name an ID to the owner (a DEC, a PRV, a requirement, a slice, a gate), add its gist in parentheses, as in `DEC-03 (weekly payouts)` or `G2 (the documents)`, and name an ID only when the owner needs it to act.<!-- /shared:id-gist -->
4. Find the workspace, the home of the status file. <!-- shared:workspace-root -->Run `recade workspace root`. It prints the folder of the workspace, the home of the project: call it `<home>`. If it exits 1, show its message, which names `recade repo sync`, and stop.<!-- /shared:workspace-root --> `slices/STATUS.md` is generated in the workspace, never edited on a slice branch, so every status move of this command is run as `recade slices status --set '<S-nn>' <status> --project '<home>'`. Read the sheets and `STATUS.md` from `<home>/slices`: they stay in the workspace, and a sheet is never copied into a code repository.
5. Read the sheet `<home>/slices/<S-nn>-*.md` with Read. Take from its header: `lane`, `format`, `implementer`, `branch`, `touches`, `depends_on`. From its Design section: the sheet has screens when that section is not `None.`. If there is no sheet, say so, suggest `/slice-write <S-nn>`, and stop.
6. `<base>` below is the `default_branch` of a repository in `recade repo list --json` (`main` for most, not for all): a rebase, a diff or a comparison with the base of a repository uses its own. The repositories of the slice are the prefixes of `touches:` in the order they first appear, or the only repository of the registry (`recade repo list`) when the globs have no prefix. The first one is the repository of the session. The worktree of a repository is `<home>/repos/<repo>/.claude/worktrees/<S-nn>`, on the branch of the sheet, and `<worktree>` below means the worktree of the repository a step is about.
7. Unless the lane is `no-code`, check where you are: run `git rev-parse --show-toplevel`. It must print the worktree of the first repository, `<home>/repos/<first repo>/.claude/worktrees/<S-nn>`. If it prints `<home>`, or the main checkout of a repository, say that /slice runs only in the worktree of the slice, started in the first repository of `touches:` (Claude Code reads the guard and the settings of the folder where it starts, and the status file must not change under the slice), suggest `/parallel` from the workspace and a new session in that folder, and stop. The worktrees of the other repositories must exist too, and be added to the session as additional directories (`/add-dir <worktree>`): if one is missing, say which and stop.
8. Run `recade slices check --project '<home>'`. If it exits 1, show the lines, say the sheet is not ready, suggest `/slice-check <S-nn>`, and stop.
9. Read `<home>/slices/STATUS.md` with Read. Find the row of `<S-nn>` (its status) and the rows of every slice in `depends_on`. If one of those is not `done`, name it and its status, say the slice waits for it, and stop. A dependency that is `ready-to-merge` is not `done`: the owner merges it, then runs `/board`.

## Step 2. What every dispatch holds, and how you read a report

<!-- shared:today-date -->Run `node -p "new Date().toLocaleDateString('en-CA')"` for today's date, as YYYY-MM-DD.<!-- /shared:today-date --> <!-- shared:agents-installed -->The agents are installed in `.claude/agents/`, and the rules they follow are in `.claude/protocol.md`.<!-- /shared:agents-installed --> Every prompt you send holds:

- the stage or mode name, the slice ID and its lane, the branch and the folder it works in (the worktree of each repository of the slice), `<home>` (the full path of the workspace, where the documents named in the agent files are read) and today's date;
- <!-- shared:dispatch-cli-harness -->the exact command line of the Recade CLI: `node "$RECADE_PLUGIN_ROOT/bin/recade.js"` (with the plugin folder written out when Step 0 read it from the file);<!-- /shared:dispatch-cli-harness -->
- <!-- shared:dispatch-paths -->the full paths of the files it needs, and the findings or answers it must act on, labelled as data;<!-- /shared:dispatch-paths -->
- <!-- shared:dispatch-reminder-harness -->the reminder that it cannot ask the owner anything, that it writes only the paths of its Writes section, and that it ends with the report block of `.claude/protocol.md`.<!-- /shared:dispatch-reminder-harness -->

An agent cannot run `recade repo sync`, `recade repo add`, `recade harness specialise`, `recade workspace commit`, `recade workspace auto-push` or `recade guard snapshot`, a nested shell (`sh -c`, `bash -c`, `eval`), or set `GIT_DIR`, `GIT_WORK_TREE` or `GIT_INDEX_FILE`: the guard refuses them. When a report says the guard refused one, do not run it for the agent to get round the guard: tell the owner.

Where files go. Documents of the workspace (the sheet, the DEC files, the designs) are written there, through the `workspace:` lines of the agent's Writes. A build, an APK or an export goes to `<home>/artifacts/<repo>/<S-nn>/`, a draft to `<home>/tmp/<S-nn>/`, and nothing is made in a new folder beside the code: both folders are outside git. The tracking sheet (`tracking.md`), the journal (`journal.md`), the pull request body (`pr.md`), the merge notes (`merge-notes.md`) and the human actions (`human-actions.md`) of the slice are in `<home>/tmp/<S-nn>/` too (spec 6.14): they are private, and never in a code repository, a commit or the body of a pull request.

Several repositories. Each step below that names the tree, a commit, a rebase, a gate or a pull request is done for each worktree of the slice in turn: git with `git -C '<worktree>'`, a gate with `recade gate run '<name>' --project '<worktree>' -- sh -c '<command>'`. Each repository has its own stamps, and the slice is green when the required gates are green in each of its repositories. The ledger holds one line for each repository.

Model and effort: in the `standard` lane, dispatch each agent as installed. In the `sensitive` lane, read the front matter of `.claude/agents/<agent>.md` before each dispatch: when it has `sensitive_model` and `sensitive_effort` (written from `harness/models.yaml` by `recade harness models`, which prints them as `Sensitive lane:` lines), dispatch the agent with that model and that effort. Never pick a model yourself.

<!-- shared:report-handling -->Read each report block. Show the owner the Human actions, in order. An agent never asks the owner: when its report holds a question, ask it yourself with `AskUserQuestion`, as a closed multiple choice with a recommended option and a safe default.<!-- /shared:report-handling --> <!-- shared:collect-reports -->Collect the report of every agent you dispatched before you end your turn: a turn never ends on "waiting for the agents". A task that already fits one agent is not split again.<!-- /shared:collect-reports -->

How you record what happened:

- **Status.** An agent never writes a status. Its report says `Status: <new status>`. You record the move yourself with `recade slices status --set '<S-nn>' <status> --project '<home>'`. The statuses are exactly: `todo`, `design`, `spec`, `gate-1`, `tests`, `implementation`, `audit`, `gate-2`, `ready-to-merge`, `done`, `blocked`. If the command exits 1, the move is not allowed: show its message, which lists the allowed next statuses, and stop.
- **Verdicts.** Take the verdict word as written: spec `READY | GAPS`, audit `CONFORMS | CONFORMS_WITH_RESERVATIONS | FIX | REOPEN`, design `ON_DIRECTION | FIX`, second opinion `CONCURS | CONCERNS | BLOCKING`. A word outside these sets is a missing verdict: ask the agent once for it, then stop as below.
- **BLOCKING and two failures.** When a report holds a `BLOCKING` line other than `none`, when `recade guard audit` prints a `BLOCKING:` line, or when the same step fails twice, stop. Show the blocking text to the owner exactly as written. Before you stop, record the cost as in Step 13 point 1. Record `recade slices status --set '<S-nn>' blocked --note '<one line of the cause>' --project '<home>'` (the note is one line, at most 200 characters, in single quotes), and stop. Never try a third variation of a failed step.
- **Guard snapshot and audit.** The guard reads command lines and is a deny list, so the structural barrier is an audit. At the start of the session (Step 3), run `recade guard snapshot --slice '<S-nn>'`: it records the main checkout of every code repository, every worktree that is not on the branch of the slice, and the workspace, and it prints the path of its file. Write that path in the ledger. Before each gate (Step 7 and Step 12), run `recade guard audit --since '<snapshot file>'`. Exit 0 says nothing changed outside the slice. Exit 1 prints one `BLOCKING:` line for each change in another repository or in a workspace path the slice may not write: any such line stops the slice. Show the lines to the owner as written, never undo the change yourself, and stop as in the BLOCKING rule above. Exit 2 is an unreadable snapshot or a wrong folder: do not take a new snapshot to get rid of it, since it would hide what changed. Say so to the owner, and stop. `recade guard snapshot` refuses to overwrite an existing snapshot (exit 2); only the owner's explicit choice adds `--replace`.
- **Leftover files.** An agent that wrote files can leave them uncommitted. After each dispatch, run `git status --porcelain` in each worktree of the slice (also `git -C '<worktree>' status --porcelain` for the others), and `git -C '<home>' status --porcelain -- slices design decisions` for the workspace. In a code repository, if files are left, commit them, except the red test files of Step 8, which wait for Step 9: `git add` each path by name (never `git add -A` or `git add .`), then run the gates, then `git commit -m '<type>(<S-nn>): <what changed>'`, with the type `docs`, `test`, `feat` or `fix`, written in `languages.code`. In the workspace, commit the files left (a sheet from `spec-writer`, a design from a designer) through the CLI, which takes the commit lock and pushes nothing: `recade workspace commit --paths '<path>[,<path>...]' -m 'docs(<S-nn>): <what changed>' --project '<home>'`. Workspace files carry no gate and no stamp, and a path that is not a document of the workspace (a state, a hook, a folder of code) is refused. Never commit the workspace with git yourself. Do not add any attribution line.
- **Gates before every commit.** The pre-commit hook runs `recade gate check` and refuses the commit when a required gate has no green stamp for the tree. The required gates of that repository are its own: `recade harness set --required-gates` writes them to `harness.required_gates` of `.claude/recade.yaml` in the repository, not to the state. Run `recade gate check --project '<worktree>'` in each worktree of the slice: it prints one line `<name>: <status>` for each required gate (from `.claude/recade.yaml`, or from the state when the repository sets none), and `No required gates` when there is none. Its exit 1 only says that a gate is not green yet: keep the names. So before every commit of this command, after the `git add`, run `recade gate run '<name>' -- sh -c '<command>'` for each required gate of that repository, with the command of its row in the `## Verification commands` table of `.claude/protocol.md`. A red gate means the commit waits: fix the cause through the step that owns it, never by skipping the hook.
- **Ledger.** The file `.recade/slices/<S-nn>/progress.md` is the memory of this command. Create it in Step 3 (the `no-code` lane has none) and update it after every step: the step done, the verdicts, the FIX loops so far, the commits, the PR. After any interruption or compaction, read it again before you do anything else.

## Step 3. Branch, ledger and cost

The `no-code` lane skips this step: no branch, no rebase, no ledger. Go to Step 4.

1. Check the branch. Run `git branch --show-current`, and `git -C '<worktree>' branch --show-current` for each other repository of the slice. Each must be the `branch` of the sheet. If one is not, say that the slice runs on that branch in its own worktree in each repository (`recade parallel plan --json` names them, `/parallel` opens them), name the folder, and stop.
2. The tree must be clean: `git status --porcelain --untracked-files=all -- . ':(exclude)slices/STATUS.md'` prints nothing (the status file is the one change that does not count). One exception: when resuming at `implementation`, the red test files that the ledger lists under `Red tests:` may be there, uncommitted, if the sha256 of each one is still the one the ledger records (compute it as in Step 8). A listed red test that is missing while its copy in `.recade/slices/<S-nn>/red/` has the recorded hash (an interruption during a task commit of Step 9) is restored first: copy it back with Read and Write, then check its hash. The copy stays. Any other line, a missing file with no such copy, or a hash that differs, is dirt. If the tree is not clean, show the lines, say the owner must commit or set the changes aside, and stop.
3. Rebase on the default branch at the start, in each worktree: `git rebase '<base>'`, unless the ledger already holds a pull request, or the red tests of Step 8 are waiting uncommitted (resuming at `implementation`: the rebase of Step 10 comes after their commit). If it stops on a conflict, run `git rebase --abort`, tell the owner which files conflict, suggest `/merge-order`, and stop.
4. Create `.recade/slices/<S-nn>/progress.md` with Write if it does not exist. It holds: the slice, the lane, the format, `Started:` with the number printed by `node -p "Date.now()"`, `FIX loops: 0`, `REOPEN loops: 0`, `Owner returns: 0`, `Snapshot:` empty, `PR:` empty (one line for each repository of the slice), `Second opinion:` empty, and, for a `large` slice, the table of tasks (task, status, commit, decisions). If it exists, read it and keep its `Started:` value, its counters, its PR and its second opinion.
5. The guard snapshot. If the ledger already holds a `Snapshot:` path and that file is readable, this is a resumed run: keep the snapshot, and run `recade guard audit --since '<snapshot file>'` now (Step 2). A `BLOCKING:` line stops the slice. A new snapshot would hide what changed between the two sessions, so take one only when the owner says so after seeing the audit: ask with `AskUserQuestion`, "The audit of the first snapshot is clean. Keep it?" Options: `Keep it` (the default) and `Take a new snapshot`. On `Take a new snapshot`, run `recade guard snapshot --slice '<S-nn>' --replace`: without `--replace` the command refuses to overwrite the snapshot file. Write the path it prints in the ledger. Otherwise (no path, or the file is gone) run `recade guard snapshot --slice '<S-nn>'`, write the path it prints in the ledger, under `Snapshot:`, and say in one line that it is new. The work already done is on the branches of the slice, which the audit does not watch, and the workspace paths of the slice are allowed.
6. Cost records. Run `recade help` once. If its output has a line that starts with `recade cost`, the project can record cost, and Step 13 does it. If it has no such line, skip every cost record without a word. Note whether that line also mentions `--transcript`: if it does, Step 13 passes the session transcript so the tokens are real counts; if not, Step 13 records the minutes and the FIX loops only.

## Step 5. Design (sensitive lane, only when the sheet has screens)

1. If the status is not already `design`, run `recade slices status --set '<S-nn>' design --project '<home>'`.
2. Dispatch `ux-designer`. It gives two or three variants and stops. Show the owner each variant in one sentence and ask with `AskUserQuestion`, in `languages.chat`: "Which variant for <S-nn>?" Options: one for each variant, with its cost to build, the recommended one marked, and `Not yet`. On `Not yet`, stop: the status stays `design`.
3. Dispatch `ui-designer`, mode `spec`, with the owner's choice labelled as data. Read its report.
4. If the report says the direction or the tokens must change first, tell the owner to run `/design direction`, and stop.
5. Go to Step 6.

## Step 6. Spec

1. If the status is not already `spec`, run `recade slices status --set '<S-nn>' spec --project '<home>'`. (From `todo`, `design`, `gate-1` when the owner refused, `tests` or `audit` on a `REOPEN`, and `gate-2`, this move is allowed.)
2. Dispatch `spec-writer`, mode `check`. The `standard` lane needs a short spec. The `sensitive` lane needs the full spec: invariants, failure cases, migration and rollback. On a reopen, hand it the reason as data.
3. `sensitive` lane: when it says `READY`, dispatch `domain-reviewer`. Read its verdict.
4. On `GAPS` from either one: ask the owner each question of the report with `AskUserQuestion`, then dispatch `spec-writer`, mode `revise`, with the findings and the answers as data. Check again. At most two rounds of `revise`. If a gap remains after that, record the move to `blocked` as in Step 2 and stop.
5. After a change of the sheet, run `recade slices check --project '<home>'` and `recade lint-style '<sheet>'`. Both must pass. Commit what is left (Step 2).
6. When the verdicts are `READY`: the `sensitive` lane goes to Step 7. The `standard` lane runs `recade slices status --set '<S-nn>' tests --project '<home>'` and goes to Step 8.

## Step 7. Gate-1 (sensitive lane): a human reads the full spec

1. If the status is not already `gate-1`, run `recade slices status --set '<S-nn>' gate-1 --project '<home>'`.
2. Run the guard audit (Step 2). A `BLOCKING:` line stops the slice here, before the owner is asked. Show the owner: the full path of the sheet, its goal in two lines, the frozen decisions, the invariants and the failure cases, the DoD rows, and the verdicts of `spec-writer` and `domain-reviewer` as written.
3. Ask with `AskUserQuestion`, in `languages.chat`: "Approve the spec of <S-nn> (gate-1)?" Options: `Approve (gate-1)`, `Change the spec`, `Not yet`. Default: `Not yet`.
4. Only after the answer `Approve (gate-1)`, run `recade slices status --set '<S-nn>' tests --project '<home>'` and go to Step 8. Nothing else moves the slice out of `gate-1`.
5. On `Change the spec`, ask in the chat what to change, run `recade slices status --set '<S-nn>' spec --project '<home>'`, dispatch `spec-writer`, mode `revise`, with the answer as data, and go to Step 6.
6. On `Not yet`, say the slice waits at gate-1 and that `/slice <S-nn>` resumes it. Stop.

## Step 8. Tests

1. Dispatch `test-engineer`. It writes one failing test for each DoD line and each guardrail, each seen red for the right reason. It writes only test paths.
2. If its report says `Status: spec`, the sheet is not clear enough. Run `recade slices status --set '<S-nn>' spec --project '<home>'`, show the owner the gaps it names, and go to Step 6.
3. Check the report: each DoD line and guardrail has a test, each with raw red output as proof. A line without proof sends the step back to `test-engineer` once. A second miss is a failure of the step: stop as in Step 2.
4. Do not commit the tests. They are red by design, and the pre-commit hook refuses a commit while a required gate is red. Nothing is committed at this step: the `test-engineer` writes only test paths, and they stay uncommitted in the worktree of the slice until Step 9 commits them with the implementation.
5. Record the red run in the ledger, under `Red tests:`, as the TDD evidence: the command run, its exit code (not 0), and one line for each test file the `test-engineer` wrote or changed (`git status --porcelain --untracked-files=all` lists each file, also in a new folder) with its sha256, from `node -e "const c=require('crypto'),f=require('fs');for(const p of process.argv.slice(1))console.log(c.createHash('sha256').update(f.readFileSync(p)).digest('hex')+'  '+p)" '<file>' ...`. When Step 8 runs again (a reopen, a spec change), it replaces the list and says why in the ledger.
6. Run `recade slices status --set '<S-nn>' implementation --project '<home>'` and go to Step 9.

## Step 9. Implementation

1. If the status is not already `implementation`, run `recade slices status --set '<S-nn>' implementation --project '<home>'`. (From `tests`, from `audit` on a `FIX`, from `gate-2` or `ready-to-merge` on a fix.)
2. Choose the agent. It is the `implementer` of the sheet, `implementer-critical` when the sheet says so. After the second `FIX` of the same slice (the counter in the ledger), the agent is always `implementer-critical`, and you say so in one line. A third `FIX` is the end: record `blocked` as in Step 2, quote the findings, and stop.
3. Format `small`: dispatch the agent once, with the sheet, the failing tests and, after a `FIX`, the findings as data.
4. Format `large`: the slice is built in tasks, one after the other, through the `superpowers:subagent-driven-development` skill (load it with the Skill tool). You are its controller, and the work lives in fresh agents and files, not in this conversation.
   - Read the tasks of the sheet. There are at most 12. If there are more, say the sheet must be split, suggest `/slice-check <S-nn>`, and stop.
   - Write the tasks in the table of the ledger. After each task, update its status, its commit and its decisions. After any interruption or compaction, read the ledger first and start at the first task that is not done.
   - Each task goes to a new agent (the one chosen in point 2) with only its own task, the sheet and the findings of the previous review. Each task is reviewed before the next one starts, by a fresh `reviewer` that reads the task and its diff. One commit for each task, named after the task, with the red test files it turned green. The red test files of later tasks are still red, so they are set aside for the commit, in this order: check their hashes as in point 6; copy each one with Read and Write to `.recade/slices/<S-nn>/red/<its path>` (the fingerprint of the gates skips `.recade/`); delete each one from the tree with `rm '<file>'` (the guard allows it only for a file git does not track); run the gates; commit; copy them back with Read and Write to their paths; check their hashes against the ledger again. The copies stay: `.recade/` is ignored by git and skipped by the fingerprint, and the next task commit overwrites them. A hash that differs at either check is a failure of the step: stop as in Step 2.
   - Tasks run one after the other. The caps of the sheet apply to each task.
   - After the last task, the audit of the whole slice is Step 10.
5. Make sure the gates of the sheet ran and are green for the current tree: `recade gate check`. If it exits 1, send the agent back once to run them and fix. A second red is a failure of the step: stop as in Step 2.
6. Check the red tests before the commit: compute the sha256 of each file listed under `Red tests:` in the ledger, as in Step 8. Each one must be unchanged, unless the ledger records why it changed (a return to Step 8 records new hashes). A test file that changed with no such record was weakened or rewritten during the implementation: that is a failure of the step. Stop as in Step 2 and never commit it.
7. Commit the test files together with the implementation (Step 2), in each repository where they are: the required gates are green now in each of them. Write each commit in the ledger. Go to Step 10.

**Flaky tests.** A test that fails and then passes with no change of the code is never deleted, skipped by hand or retried until it passes. Tell the owner, and when the owner agrees, record it with `recade quarantine add '<test>' --reason '<reason>' --slice '<S-nn>' --project '<worktree>'`, where `<worktree>` is the worktree of the repository that holds the test (each repository has its own `tests/quarantine.json`, and the command writes the one of the checkout it runs in), and commit `tests/quarantine.json` in that repository. The blocking rows of the technical sheet (Test, Contract tests, E2E tests, Confirmation tests and Accessibility tests) must skip the tests listed by `recade quarantine list --names`. The increment cannot close while the test stays quarantined (`/retro`).

## Step 10. Audit

1. Rebase on the default branch, in each worktree: `git rebase '<base>'`, unless the ledger already holds a pull request (a rebase would rewrite its history; then skip it). On a conflict, run `git rebase --abort`, tell the owner, suggest `/merge-order`, and stop.
2. Run `recade slices status --set '<S-nn>' audit --project '<home>'`. (From `implementation`. When resuming at `audit`, skip this.)
3. Dispatch the reviewers one after the other, each with the sheet and the branch, never with the report of another reviewer:
   - `reviewer`, always (mutation on the guardrails, gates re-run by itself);
   - `security-reviewer`, in the `sensitive` lane or when the sheet touches security. In the `sensitive` lane, dispatch it with the `sensitive_model` and `sensitive_effort` of its front matter (Step 2);
   - `design-reviewer` and `product-reviewer`, when the sheet has screens. Hand them the screenshots paths and the job of the user in plain words.
4. Take the strongest verdict, in this order: `REOPEN`, `FIX`, `CONFORMS_WITH_RESERVATIONS`, `CONFORMS`. A design verdict `FIX` counts as `FIX`, and `ON_DIRECTION` as `CONFORMS`.
   - `FIX`: add 1 to `FIX loops` in the ledger, then go back to Step 9 with the findings as data.
   - `REOPEN`: add 1 to `REOPEN loops`. At most 2 reopens are allowed: on the third, record `blocked` as in Step 2, quote the reason, and stop. Otherwise run `recade slices status --set '<S-nn>' spec --project '<home>'`, and go to Step 6 with the reason as data. In the `sensitive` lane the spec then comes back to gate-1.
   - `CONFORMS_WITH_RESERVATIONS`, `standard` lane: ask with `AskUserQuestion`: "The audit has reservations on <S-nn>. What now?" Options: `Accept the reservations` (the slice goes on, the merge notes list them), `Back to implementation` (the findings go to the implementer). Default: `Back to implementation`. On `Back to implementation`, add 1 to `Owner returns` (the owner's own counter, not the `FIX loops` that decide the escalation) and go to Step 9.
   - `CONFORMS_WITH_RESERVATIONS`, `sensitive` lane: carry the reservations to the merge notes and to gate-2.
   - `CONFORMS`: go on.
5. Write the verdicts in the ledger, and go to Step 11.

## Step 11. Documentation, pull request and second opinion

1. Dispatch `doc-writer`. Commit what is left (Step 2).
2. Rebase on the default branch once more, in each worktree: `git rebase '<base>'`. Same handling of a conflict as in Step 10. If the ledger already holds a pull request, skip this rebase: it would rewrite the history of an open pull request. Tell the owner if the base moved, and suggest `/merge-order`.
   **UI slice: the demo.** When the sheet has screens (its Design section is not `None.`), the pull request body carries a demo, so the owner sees the change without running it. Run `git ls-files --cached --others --exclude-standard 'docs/suivi/<S-nn>/screens' 'docs/suivi/<S-nn>/demo'` and read the list. It must hold the screenshots of the Playwright run (the end to end command of the sheet, with screenshots on), one for each screen and each state, or a short recording of the run (video on, at most 60 seconds and 10 MB) under `docs/suivi/<S-nn>/demo/`. If neither is there, dispatch `design-reviewer` once to take the screenshots with the project's end to end tool and save them under `docs/suivi/<S-nn>/screens/`. A second miss is a failure of the step: stop as in Step 2, and never open the pull request without a demo. Commit the demo files by name (Step 2) before the release manager runs, and give it their paths. A slice without screens has no demo section.
3. Find the workspace issue of the slice, the one the pull requests point to. The board record is in the workspace: `github` of `recade state show --json` gives `owner` and `repo` (the workspace repository), and `github.links`, when it names `<S-nn>`, gives the issue the owner confirmed: a number is an issue of the workspace repository (`https://github.com/<owner>/<repo>/issues/<n>`), a text is already a full issue URL. Without a link, run `gh issue list --repo '<owner>/<repo>' --state all --limit 1000 --json number,title,url` (a search option is not used: a search can miss an issue that was just created) and keep the issue whose title is exactly `[<S-nn>]` or starts with `[<S-nn>] `. Its `url` is the full URL `https://github.com/<owner>/<repo>/issues/<n>`: give it to the release-manager, and tell it to write it as `Slice issue: <url>` in the body of every pull request of the slice, never as `Closes #<n>`. Two issues that match, or a list of exactly 1000 rows with no match (it may be cut short), is not a board that is not set up: say so, ask the owner with `AskUserQuestion` which issue it is (or to set `github.links`), and stop. Only with no `github` record, or a list of fewer than 1000 rows with no match, is the board not set up: say so in one line, and tell it to write `Slice issue: not on a board yet`. Dispatch `release-manager` once for each repository of the slice, with that repository's worktree and its own line of the ledger. Tell it to run the gates for the current tree and to write the pull request body, the merge notes and the human actions in `<home>/tmp/<S-nn>/`, which are never committed. If the ledger holds no pull request number, tell it to open the pull request from the slice branch of that repository. If the ledger holds a number, the slice came back after the pull request was opened: never open another. Tell it to update that pull request, which means sending the new commits to the same branch and refreshing the body from the body file, and give it the number. Tell it the verdicts and reservations of Step 10, labelled as data, to quote in the merge notes and never in the body of a pull request: the body holds the technical summary of the change, the test evidence and the workspace issue URL only, never a DoD row, a decision or text of the sheet. Show the owner the merge notes before the merge question. For a UI slice, tell it that the body must carry the demo, and hand it the paths of the screenshots or of the recording. Read its report: the pull request number and the stamps. Write the number in the ledger (`PR:`). If a stamp is stale, send it back once. A second miss is a failure of the step.
4. Count the changed lines of each pull request: `gh pr view '<PR>' --json additions,deletions` run in the worktree of its repository, and add the two numbers. A slice has one pull request in each repository, all on the same branch, and the second opinion follows the sum of them.
5. The second opinion follows `second_opinion` of the state. With `off`, it is never run: say so in one line and go to point 7. With `always`, it runs for every pull request. With `sensitive` (the default), it runs when the lane is `sensitive` or when the pull request changes more than 400 lines. When it is due, go on to point 6. When it is not due, say so in one line and go to point 7.
6. Run the second opinion once for each state of the diff. Take `git rev-parse HEAD` and compare it with the commit written under `Second opinion:` in the ledger. If they are the same, or `git diff --quiet '<recorded commit>' HEAD` says the diff is the same, do not run it again: show the recorded verdict. Otherwise run `/second-opinion <PR>` for the pull request of the first repository, and `/second-opinion <PR> --repo '<repo>'` for the one of each other repository: the session is started in the first repository, and the option names the repository whose pull request it is. That command is defined by the harness (Task 8), and it gives the agent only the pull request, the sheet and the requirements the sheet cites, never the reports. Take the verdict from its answer, one of `CONCURS | CONCERNS | BLOCKING`, and write the verdict and the commit under `Second opinion:` in the ledger. If the project has no `/second-opinion` command yet (there is no `.claude/commands/second-opinion.md`), say "Run /second-opinion <PR> when available." and note in the ledger that the second opinion is not done. Do not invent a verdict.
7. Go on to Step 12.

## Step 12. Gate-2 or ready to merge

**The Definition of Done is ticked before the merge.** The `Done` column of the DoD table of the sheet starts as `[ ]`. `/board` marks the slice `done` only when every pull request of the slice is merged and every line is `[x]`, so an unticked sheet blocks `done`. The owner ticks at gate-2 (or at the standard lane question below), before the merge. The sheet is in the workspace, so the ticking is made there, through the CLI, and never in a code repository. It is done here, after the owner's answer, never before: for each DoD line, run `recade slices dod '<S-nn>' --tick <n> --project '<home>'` (`<n>` is the number in the `#` column; several `--tick` options tick several lines at once) only when `recade gate check '<name>'` prints `green` for the current tree of the repository where that line's command runs, or the owner said in the answer that the line was seen green. The command edits the `Done` cell of that row only, in `<home>/slices/<S-nn>-*.md`, and commits the sheet in the workspace under the commit lock (`docs(slices): tick DoD row <n> of <S-nn>`), with no push. If it exits 1 because the sheet has changes of its own that the step did not make, show its message and stop: the owner commits them first. Never tick a line that was not seen green, and never edit the sheet by hand or commit it with git. Leave such a line open and say which lines are open. That commit is in the workspace, so it changes no `HEAD` of a code repository and no gate stamp goes stale. Run `recade gate check` in each worktree of the slice: every stamp must be green for the current tree. If one is stale or red, send the step back to `release-manager` once, in update mode as in Step 11 point 3, with the number from the ledger (`PR:`) of that repository: never open another pull request. A second miss is a failure of the step: stop as in Step 2. Run the guard audit (Step 2): a `BLOCKING:` line stops the slice. Only then run the `ready-to-merge` move. The move never comes before the sheet is ticked and committed, the gates are green in every repository and every pull request of the slice is open.

**Sensitive lane: gate-2.**

1. If the status is not already `gate-2`, run `recade slices status --set '<S-nn>' gate-2 --project '<home>'`.
2. Show the owner: the address of each pull request, each reservation of the audit and each open concern, as written, and the verdict of the second opinion with its comment link (or "not done" when it was not run).
3. A `BLOCKING` stops gate-2: pass it to the owner as written, never softened, and do not offer `Approve (gate-2)`. Offer `Back to implementation`, `Back to spec` and `Not yet`.
4. Otherwise ask with `AskUserQuestion`, in `languages.chat`: "Approve <S-nn> at gate-2?" Options: `Approve (gate-2)`, `Back to implementation`, `Back to spec`, `Not yet`. A `CONCERNS` verdict is the owner's to decide here: say so in the question. Default: `Not yet`.
5. Only after the answer `Approve (gate-2)`, tick the Definition of Done and check the gates as described above, then run `recade slices status --set '<S-nn>' ready-to-merge --project '<home>'`. Nothing else moves the slice out of `gate-2`.
6. On `Back to implementation`, run the `implementation` move, add 1 to `Owner returns`, and go to Step 9. On `Back to spec`, run the `spec` move and go to Step 6. On `Not yet`, say the slice waits at gate-2 and that `/slice <S-nn>` resumes it. Stop.

**Standard lane.**

1. If the second opinion ran with `BLOCKING`, do not go on: show it as written and ask with `AskUserQuestion`: "The second opinion blocks <S-nn>. What now?" Options: `Back to implementation` and `Stop here`. Default: `Stop here`. `Back to implementation` adds 1 to `Owner returns` and goes to Step 9 after the `implementation` move.
2. If it ran with `CONCERNS`, show the points and ask: "The second opinion has concerns on <S-nn>. What now?" Options: `Go on to the merge`, `Back to implementation`. Default: `Back to implementation`, which adds 1 to `Owner returns` and goes to Step 9 after the `implementation` move.
3. When the way is clear, ask with `AskUserQuestion`, in `languages.chat`: "Tick the Definition of Done of <S-nn> and mark it ready to merge?" Options: `Tick and go on` and `Not yet`. Default: `Not yet`. Only after the answer `Tick and go on`, tick the Definition of Done and check the gates as described above, then run `recade slices status --set '<S-nn>' ready-to-merge --project '<home>'`.

## Step 13. End

1. Cost records: if Step 3 found `recade cost`, compute the minutes since `Started:` with `node -p "Math.round((Date.now() - <Started>) / 60000)"`, then run `recade cost record '<S-nn>' --minutes <minutes> --fix-loops <FIX loops> --project '<home>'`. The record goes to the main checkout, so it survives the worktree. The minutes run from the first `Started:` of the ledger, so each record is the cumulative figure of the slice and the last one counts.
   If Step 3 saw `--transcript` in the help line, add `--transcript '<transcript>' --since <Started> --session-dir '<worktree>'` to that command, so the tokens are counted from the session itself (subagents included, each message once). Each record holds the tokens of its own window, from the later of `<Started>` and the previous record of the slice to now, so the records add up and nothing is counted twice. `<transcript>` is the `transcript_path` of the Stop hook when your context carries one. Otherwise write `auto`. `<worktree>` is the output of `git rev-parse --show-toplevel` run in the slice worktree, which is the folder this session was started in: Claude Code keeps the session under that folder, not under `<home>` (the `--project` value), so always pass it. With `auto`, the CLI takes the one session file written in that folder since the window began. If more than one session was written in the window, or none, it records `tokens: not recorded` and lists the candidates: it never guesses, so do not pick one for it. When the CLI prints `tokens: not recorded` with a reason, the minutes and the FIX loops are recorded anyway: say so in one line and go on. Never type a token figure yourself and never pass `--tokens` by hand.
2. Tell the owner, in a few lines: the address of each pull request, one for each repository, the human actions of the release manager in order, and the verdicts. Tell the owner to read the pull request and merge it, then run `/board` from the workspace. A slice that touches several repositories has one pull request in each: they are merged in the order of `merge_order:` of the sheet, or of the prefixes of `touches:` (the API before the web). The ticked Definition of Done is in the sheet of the workspace, and `/board` reads it there. You never merge, and `/board` is what marks the slice `done`.

## Step 14. The no-code lane

The DEC file is the work. Follow the flow of `/decision` with the Goal of the sheet as the topic. When the owner chooses (`recade decision close`), run `recade slices status --set '<S-nn>' done --project '<home>'`. If the owner does not choose now, say the slice stays `todo` and `/slice <S-nn>` resumes it. Stop.

## Limits

This command never runs `recade repo sync` or `recade repo add` (the owner does, from the workspace), never writes in a code repository that the slice does not touch, never runs a merge, never pushes to `main`, never uses `--no-verify`, never deletes or weakens a test and never writes a status by hand: the status moves above are the only ones. It passes neither gate-1 nor gate-2 without the owner's answer to the question of that step.
