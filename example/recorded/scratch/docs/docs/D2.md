## 1. Purpose, principles and scope

### 1.1 Purpose

D2 describes how the desk is built. It follows D1 and the stack decision in `docs/STACK.md`.

### 1.2 Architecture principles

- One process and one data file, so a volunteer can restart it (ADR-01, one small server).
- A rule that protects a tool is enforced in the data layer and covered by a test (PRI-01, a tool is never lent twice).

### 1.3 Built versus target

Nothing is built yet. Every component below is target.

## 2. Context, containers and boundaries

### 2.1 Context (C4 level 1)

Volunteers use the desk screen in a browser on the library's laptop. The screen talks to one server in the library.

### 2.2 Containers (C4 level 2)

| Container | Role |
|---|---|
| Desk web app | Pages for loans, returns, tools and members |
| Desk server | Rules, the late fee and the overdue report |
| Data file | One SQLite file on the server |

### 2.3 Trust boundaries

The desk server trusts the library network only. D3 lists the boundary as TB-1 (the library network edge).

### 2.4 Environments

A test environment on a volunteer's laptop, and the library server.

### 2.5 Repository layout

| Repository | Holds | Visibility |
|---|---|---|
| api | The desk server: rules, the late fee and the overdue report | private |
| web | The desk web application: pages for loans, returns, tools and members | private |

fernhill-lending-workspace/

    web/

## 3. Infrastructure and cost

### 3.1 Infrastructure

One small virtual server with a daily backup.

### 3.2 Monthly cost estimate

About 15 per month (PROVISIONAL, PRV-03).

## 4. CI/CD

Every pull request runs the tests and the style check. A merge to `main` deploys by copying the build to the server and restarting it.

## 5. Data model and integrity

### 5.1 Model

Four tables: tools, members, loans, settings.

### 5.2 Integrity rules

A tool has at most one open loan. The data file enforces it with a unique index (PRI-01, a tool is never lent twice).

## 6. API conventions

The desk server returns JSON. An error carries a plain sentence that the screen shows to the volunteer.

## 7. Applications and async jobs

### 7.1 Web and mobile applications

One web application for the desk. No mobile application.

### 7.2 Asynchronous jobs

One nightly job builds the overdue report for FR-REP-01 (the overdue list).

## 8. Domain engines and integrations

The late fee engine is a pure function of the due date, the return date, PAR-02 (late fee per day) and its cap (DEC-02, the late fee cap). There is no integration.

## 9. Security summary

Sessions expire after 15 minutes. D3 holds the requirements.

## 10. Observability, backup, recovery and capacity

The server logs each request without personal data. The data file is copied every night. 500 members fit easily in one file.

## 11. Technology stack and quality gates

### 11.1 Tech stack

Node 22 with the built-in HTTP server, test runner and SQLite module (ADR-01, one small server).

### 11.2 Quality gates

Tests and the style check must pass before a merge.

### 11.3 Test strategy

One test file for each rule. The border of a rule has its own test: the loan on day 7 and day 8.
