## Step 2. The slicing formula

Ask with `AskUserQuestion`, in `languages.chat`: "How should the plan be sliced?" Options, in this order:

1. `Mixed (recommended)`: large orchestrated slices for the core, small parallel slices for the rest.
2. `Small parallel slices`: 3 to 5 slices at a time, one pull request for each. For several reviewers and raw speed.
3. `Large orchestrated slices`: one slice for each feature, cut into tasks, one pull request. For one reviewer who wants fewer interruptions.

If the owner typed another answer instead of choosing an option, ask again once, then use `Mixed`. Only after the answer, run `recade state set slicing '<mixed, small or large>' --project '<dir>'`. Tell the owner the formula in one line, and that `/recade:amend` can change it later.

## Step 3. Cut

<!-- shared:today-date -->Run `node -p "new Date().toLocaleDateString('en-CA')"` for today's date, as YYYY-MM-DD.<!-- /shared:today-date -->

<!-- shared:writer-model-read -->Read the writing model once: run `recade models writer` and keep the word it prints (`fable` or `opus`).<!-- /shared:writer-model-read --> Pass it as the `model` of the Agent tool in every dispatch of a writer-tier agent (here the `slicer`, for `cut`, for `next` and for every `revise`). <!-- shared:writer-model-rule -->It is the owner's choice between Fable and Opus, at the same effort. Never write the full id in a dispatch, and never run the command again for the next dispatch.<!-- /shared:writer-model-rule -->

Dispatch `slicer`, stage `cut`. Its prompt holds:

- the stage name, the full path `<dir>`, today's date, and `languages.work` for the sheets;
- the slicing formula from Step 2, the `hotspots` list, and the mode (`adopt` means code exists, so the slice S-00 inventory is needed);
- the registry of the code repositories (the output of `recade repo list --json`), and the rule that every glob of `touches:` is written `<repo>:<glob>` once there are two repositories or more (the prefix is optional with one), that a slice across repositories may add `merge_order:` to name the order of its pull requests, and that `workspace:` is never a prefix of `touches:`;
- <!-- shared:dispatch-cli-plugin -->the exact command line of the Recade CLI: `node "${CLAUDE_PLUGIN_ROOT}/bin/recade.js"`, and the reminder to add `--project '<dir>'`;<!-- /shared:dispatch-cli-plugin -->
- the full path of the template: `${CLAUDE_PLUGIN_ROOT}/templates/slice.md`;
- the track (`full` or `short`). In the short track, S-01 is a walking skeleton, marked `skeleton: true` in its header, the first increment holds S-01 plus at most 5 slices (6 sheets), and the rest of the PLAN goes to `slices/BACKLOG.md`, one row for each later slice with its gist and its stories;
- <!-- shared:dispatch-reminder-plugin -->the reminder that it cannot ask the owner anything and writes only the paths of its Writes section.<!-- /shared:dispatch-reminder-plugin -->

For the next increment of the short track (point 5 of Step 1), the stage is `next` instead of `cut`, with the same prompt and the same writing model as `cut`.

Read its report. Keep the values it could not find and the gaps it reports for the owner.

## Step 4. Checks

1. Run `recade slices check --project '<dir>'`. It must exit 0. On exit 1, dispatch `slicer` with the stage `revise` and the lines of the output, labelled as data. A line that points to `docs/PLAN.md` is fixed in the sheets, not in the PLAN. A line `touch-prefix` (a glob with no repository while there are two or more), `touch-repo` (a repository that is not in the registry, or `workspace:`) or `touch-empty` (a prefix with no glob) is fixed in the sheet that holds it. At most 2 rounds. If an `error` is still there after that, show the lines to the owner, say that the slices cannot be approved before they are fixed, and stop.
2. Run `recade lint-style slices --project '<dir>'`. A line with `error` goes back to `slicer` with the stage `revise`.
3. Run `recade index check --project '<dir>'`. A finding that points to a sheet goes back to `slicer` with the stage `revise`. A finding that points to D1, D2, D3, `STACK.md` or the BIBLE is not fixed here: tell the owner, in one line, and say it waits for `/recade:amend`.
4. After any fix, run points 1 to 3 again, until none prints an `error` that points to a file of the phase. Warnings (`slice-hotspot`, and `slice-skeleton` and `slice-cap` in the short track) are shown to the owner, one line each, and are not blocking. A `slice-skeleton` or `slice-cap` warning goes back to `slicer` with the stage `revise` once.

## Step 5. Graph and status

1. Run `recade slices graph --project '<dir>'` and `recade slices status --project '<dir>'`. They write `<dir>/slices/graph.md` and `<dir>/slices/STATUS.md`.
2. Show the owner what was written: for each slice, its id, name, format and the slices it waits for, which slices can start at once, the hotspots and how the slices that touch them are ordered, the full paths of `slices/graph.md` and `slices/STATUS.md`, in the short track the number of later slices in `slices/BACKLOG.md` with the gist of the first three and the way to cut them (run `/recade:slices` again once the first increment is done), and the provisional values still open (`recade provisional list --open --project '<dir>'`).

## Step 6. Where the code lives, and G4

### 6.1 The forge

Run `recade state show --json --project '<dir>'` and read `forge` and `forge_asked`. When `forge_asked` is true, the owner chose already: go to 6.2 for `local` and to 6.3 for `github`, and do not ask again. Otherwise ask once with `AskUserQuestion`, in `languages.chat`: "Where should the code live?" Options, in this order:

1. `Local only (default)`: git on this machine; nothing leaves it; the board is `slices/STATUS.md`, and a slice ends with a review request in the workspace that the owner merges.
2. `GitHub`: private repositories, a board, issues and pull requests.

If the owner typed another answer instead of choosing an option, ask again once, then use `Local only`. Only after the answer, run `recade state set forge '<local or github>' --project '<dir>'`. Say in one line that the choice can change later: `recade state set forge github`, then `recade github init` creates the repositories and the board as in 6.3. In mode `adopt`, on `Local only`, `recade adopt board` is not run: nothing is read on GitHub. Then go to 6.2 for `local` and to 6.3 for `github`.

### 6.2 Local only

Nothing in this part calls `gh`, runs `recade github init` or pushes. The code repositories keep the remote `none` that `recade repo add --new` gave them.

1. Commit the slices in the workspace: `git -C '<dir>' add slices recade`, then `git -C '<dir>' commit -m "docs(slices): slice sheets"` (skip it when Git says there is nothing to commit). Write the message in `languages.code`. Do not add any attribution line. If Git fails, show the error in one line and go on.
2. Tell the owner in a few lines: the sheets, `slices/graph.md` and `slices/STATUS.md` are committed in the workspace, `STATUS.md` is the board, and each slice will end with a review request in `slices/reviews/<S-nn>.md` that the owner reads and merges with git. Then ask with `AskUserQuestion`, in `languages.chat`: "The slices and the checks are done. Approve the slices (gate G4)?" Options: `Approve (G4)` and `Not yet`. Only on `Approve (G4)`, run `recade state pass G4 --project '<dir>'`, commit `recade/` again: `git -C '<dir>' add slices recade`, then `git -C '<dir>' commit -m "docs(slices): slices approved at G4"` (same rules as in point 1), then `recade state show --project '<dir>'` and tell the owner the next action in one line. On `Not yet`, ask what to change, and say that `/recade:slices` can be run again to check the sheets once more.
3. Never run `recade state pass` for any gate other than G4, and never for G4 without the owner's `Approve (G4)` in this point. This part makes exactly these commits and no other: the slices commit of point 1 and the `recade/` commit of point 2. Stop here.

### 6.3 GitHub

This part is the only one that touches GitHub. It creates the private repository of the workspace, its board, its epics (one for each lot of the PLAN, with the label `epic`) and its issues, and then, one yes at a time, the repositories of the code. It pushes only the workspace and the code repositories the owner said yes to, and nothing else. The issues live on the workspace repository. A slice sheet is private: it is never copied into a code repository, a pull request or a CI log, and no issue is created in a code repository.

When the state already records a board (`github.project_number`), this is a new cut of a project whose board exists: keep the board in line instead of points 1 to 6, then go to point 7. <!-- shared:github-sync -->Keep the GitHub board in line with the documents, only when all of these hold: `recade state show --json --project '<dir>'` shows `forge` as `github` (a missing `forge` counts as `github`), its `github` key has a `project_number`, and the owner says yes below. Otherwise skip these points and say nothing about them.
1. Run `recade github sync --dry-run --project '<dir>'`. It only reads from GitHub and prints the calls it would make: an epic for a new lot, a new title or body for an epic or a story whose PLAN text changed, a story or a slice moved to the epic of its new lot, the epic of a lot that left the PLAN closed with a comment (never deleted), and the board fields that follow the PLAN (`Epic`, and `Points`, `Priority` and `Increment` of a story). If it says `Nothing to change`, say so in one line and skip the rest of these points. If it exits 1, show the error in one line, say the board waits for it, and skip the rest of these points.
2. Tell the owner in a few lines what would change, then ask with `AskUserQuestion`, in `languages.chat`: "Bring the GitHub board in line with the documents now?" Options: `Yes, update the board` and `Not now`. On `Not now`, say that the board was not changed and that `recade github sync` can run later.
3. Only on `Yes, update the board`, run `recade github sync --project '<dir>'`. It never creates a repository or a board, never deletes an issue, and edits only the issues Recade wrote. Show the lines it printed. On exit 1, show the error in one line and say that running it again continues where it stopped.<!-- /shared:github-sync -->
